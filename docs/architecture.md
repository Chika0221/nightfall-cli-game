# 実装構成

## Linux側

- `nightfall/content.py`：固定シナリオの基準ファイルと再現可能な課題生成。
- `nightfall/scenario.json`：日本語の依頼、操作紹介、3段階ヒント。
- `nightfall/engine.py`：S1〜S10の状態遷移、認証、回収、提出、リセットとスナップショット。
- `nightfall/fs.py`：dir_fdとO_NOFOLLOWを使うプレイヤー領域への読み書き。通常ファイルのサイズを制限し、リンクを経由して管理領域へ入らない。
- `nightfall/daemon.py`：Unixソケットの単一ライター。SO_PEERCREDでcontractorまたはrootの接続だけを受け付ける。
- `nightfall/client.py`：公開する唯一のPythonコード。正解や判定定義を含まない。パスワードはgetpassで入力し、端末がない場合はエコー入力にフォールバックしない。
- `nightfall/admin.py`：運営用の環境復元、練習初期化。変更時は管理サービスを停止し、排他ロックを取る。

実行時は標準ライブラリだけを使います。管理コードはrootだけがアクセスできる `/opt/nightfall` のvenvに置き、公開クライアントは別のファイルとして配置します。開発時のパッケージをそのままプレイヤーのPythonパスへインストールしないでください。

## 進捗と復旧

SQLiteにシナリオ版、ステージ、クリア一覧、解放・回収・提出状態、開始時刻、累計プレイ時間、ヒント履歴、未完了操作、各ステージ開始時のスナップショットを保存します。

公開・回収・core解放・リセット・全体復旧は、未完了操作を先に保存し、ファイル処理後に状態を確定します。失敗時は次の要求またはサービス再起動時に未完了操作を再実行します。ソケット要求を直列化し、入力プロンプトにはステージ番号を付けて別端末の古い回答を拒否します。

全体スナップショットはプレイヤーのホームとゲーム公開領域に限定し、通常リセットではステージ所有のパスだけを復元します。S10のstagingはS9で受理したアーカイブからスナップショットを構成するため、正しいアーカイブを別の手順で作成した場合にも復元できます。

累計プレイ時間は起動シェルの開始・終了通知の間だけ加算します。サービス停止中は加算しません。標準モードでは120分後も継続できます。起動シェルのPIDとプロセス開始時刻を管理側で確認し、終了通知が失われた場合もプロセスの消滅を検出して加算を止めます。数秒単位の計測誤差はあるため、時間は学習用の参考値として扱います。

## 提出物

圧縮データを私有一時領域へコピーし、固定したデータを検証します。圧縮後1 MiB、解凍ストリーム全体8 MiB、100エントリに制限します。tar内の名前でファイルシステムへ展開せず、通常ファイルの内容をメモリで読みます。絶対パス、親ディレクトリ参照、リンク、特殊ファイル、疎ファイル、重複パス、想定外の構成は拒否します。

証拠は不変の基準データとバイト比較します。manifestはCRLFをLFに正規化して順序不問で照合し、reportは指定の2行を末尾改行の有無を許容して照合します。元の証拠の残存、READYの空内容、キャッシュと提出物の論理サイズ、oldの不在も検証します。

## Windows側

PowerShellがWSLの検出・インポート・起動・練習環境の作成を担当します。参加者用の入口は日本語名のcmdファイルです。バイナリtarの入力は.NETのStreamで渡し、PowerShell 5.1の文字列パイプラインによる破損を避けます。

`mission replay N`は管理側の固定ファイルに番号だけを記録し、Windows側がシェル終了後にroot用の固定コマンドで回収します。LinuxからWindows実行ファイルを呼び出す必要はありません。練習環境の作成には起動元のrootfsを使用します。
